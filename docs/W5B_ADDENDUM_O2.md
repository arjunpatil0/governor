# ADDENDUM O-2 — dated note on addendum O-1: c'B switches mode too; c0m redefined at a locked 1800 MHz (written 2026-10-23, BEFORE any W5b data; no trial2 has been run yet)
Source: Arjun and the reviewer, 2026-10-23, before the second trial. Addenda O and O-1 stay as committed; this note supersedes what it names.

## 1. Fairness: c'B switches pacing mode inside a cell (supersedes O-1 section 3 on c'B)
O-1 fixed c'B's mode once per cell by c0m; d'B could switch. That would let d'B win S1/S1d by switching alone. Now BOTH switch inside a cell: c'B (controllers/pi.py SwitchingPIController) by a simple NON-learned rule: unaligned when the recent measured frame time exceeds 6.57 + 0.3 ms, aligned when it falls below 6.57 - 0.3 ms, never sooner than 5 s (50 ticks) after the last switch. The frame time is the median of the last 30 frame latencies while aligned and their 10th percentile while unaligned (contended frames are longer; the low quantile is the frame alone, the estimator PIController already uses). Two PIController instances share one clock; only the executed one sees observations; the incoming one keeps its last duty / guard and gets fresh windows. d'B stays prediction-based (predicted token rate of the aligned and the unaligned plan, O-1 section 3). Tests: tests/test_pi_switch.py (8, test-first). Limitation, flagged: 6.57 ms comes from the clean 3B token (10.1 ms); a single fixed threshold is wrong for a workload with shorter tokens (the 1B token is about 4-5 ms and still fits a 12 ms frame), so c'B may go unaligned where aligned would still work; d'B uses the token time it learns. A token-aware threshold (period - measured token time - guard) would be equally non-learned; say if you want it.

## 2. The c0m puzzle (6.68 ms at nominal 7 versus 5.2 ms in smoke 3)
Evidence from the trial files (no new run): (a) trial_static locked 1500 MHz measured fg p50 8.50 ms; the nominal law predicts 7 x 1.202 = 8.41 ms (W1/B ratio at 1500): the frame calibration is RIGHT, nominal c0 = ms alone at a locked 1800 MHz. (b) The "indicative mapping 0.745" of smoke 3 is the clock ratio 1800/2460 = 0.73: that run's unlocked frames ran at the full boost clock because the background kept the GPU busy. (c) trial_fgalone read 6.68 ms = 7 x 1800 / 1886: the foreground alone, unlocked, ran at an effective clock of about 1890 MHz, not 2460, consistent with Arjun's hypothesis (the GPU, about 40% busy, does not hold boost between frames). (d) trial_arma, with the background busy, shows SM median 2460. HYPOTHESIS NOT DIRECTLY TESTED: trial_fgalone did not log the SM clock. The new foreground-alone cell logs it.
Definition (supersedes the yaml's c0m wording and O-1 section 1): c0m = p50 latency of the foreground alone at a LOCKED 1800 MHz (the clock that defines nominal c0), expected within 0.85-1.15 x nominal (the morning check flags anything else); c0m_unlocked = the same with the clock unlocked and no background, recorded alongside with the SM clock median and 10th/90th percentile of both measurements (cell.json: c0m, c0m_unlocked, sm_locked_median, sm_unlocked_median, sm_unlocked_p10_p90, c0m_over_nominal). The foreground-alone cell now takes two 15 s runs.
Decisions use the CURRENT measured frame time, never c0m: c'B's switch (section 1), d'B's plans (its frame-cost estimate is built from the live latencies and the clamped live clock), the statics fix their pacing by design. c0m no longer enters any rule (the c'B mode-by-c0m rule of addendum O section 4 is removed); it is a logged reference. The yaml's boundary statements "a token fits only if c0m <= 6.57 ms" are to be read as "if the frame time at the CLOCK RUNNING <= 6.57 ms".

## 3. Re-check of the feasibility gate and the c0 search with this definition
The gate (HW0) and the search use the NOMINAL c0 (7, 8, 9, 10, 11 ms at 1800 MHz), arm a in S1 (unlocked clock, background busy, so boost holds: SM 2460 in trial_arma), and the 70 statics at explicit clocks; none reads c0m, so they read exactly as before. What changes is the interpretation of the trial: at a LOCKED clock of at most 1800 MHz the frame is at least c0 ms; aligned pacing needs frame <= 6.57 ms, which for c0 = 7 holds only at about 1920 MHz and above, i.e. only for the 'unlocked' static (effective 2460 with the background busy), so trial_static's 0 tok/s at a locked 1500 MHz (frame 8.5 ms) was expected arithmetic, not a surprise about light frames. At c0 = 7 the feasible statics are therefore unlocked-aligned ones or unaligned duty settings; whether one meets 60 W and 20% of the background-alone rate is exactly what the sweep measures. The search order and the arm-a precondition are unchanged.
