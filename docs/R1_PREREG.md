# R1: does a local LLM hurt a real game's frames, and does a cheap fix already work? Forecast and decision rule

Branch `real-game`, written 2026-11-10, revised 2026-11-11 after the reviews recorded at the end, committed and pushed before any measurement. The rule may be amended by a separate commit until the first cell is run; no amendment after that. Smoke cells and the sweep are data.

## Terms

SOLO is the game alone. UNGATED is the game plus the LLM decoding flat out, with nothing limiting it. A hitch is a frame whose frame time is above 25.0 ms (1.5 times the 16.67 ms period). GPU busy is PresentMon's time per frame during which the GPU worked on that frame. "Build the gate" would mean building a mechanism that starts LLM work only in the GPU idle time that the game's frame cadence predicts, which is what v2 did with a hint from the app; it costs weeks of engineering and is what this sprint decides for or against.

## Question

On this laptop, under normal-user conditions, (1) does a local LLM decoding next to a real game worsen the game's frame times, (2) does a one-line fix (a lower GPU scheduling priority for the LLM process, or running the LLM on the integrated GPU) already solve it, and (3) is the game's frame timing predictable enough from outside to drive a gate with no help from the game. This sprint builds no mechanism: no pause patch, no predictor-driven gate, no clock lock, no helper.

## Conditions

The GPU runs unlocked, as for a normal user: no clock lock, no clock helper, no power-limit change. The foreground is a real Direct3D or Vulkan program capped at 60 fps, not the synthetic kernel loop. The game is the Unigine Superposition benchmark (free Basic edition), the fallback named in the brief, because no installed game has a repeatable benchmark without kernel anti-cheat (GTA V ships BattlEye; Fortnite ships Easy Anti-Cheat). Stock llama.cpp at commit 620d2225c without the pause patch in every arm, model Llama-3.2-3B Q4_K_M. PresentMon 2.6.0 console build (sha256 b2a706bc6ad475749e3b7e3409263aa1e6906d45bdcf993f6dbc0f660188f1af, signed by Intel Corporation) captures every cell, SOLO included, so its overhead is common to all arms, and the window is cut on QPC time (`--qpc_time`).

Settings that change the result are fixed, not merely recorded: AC power, the Armoury Crate mode, HAGS on or off, the display and GPU mode (dGPU-direct or hybrid), the cap method with vsync state and panel refresh rate, the Superposition preset, how the scene is started (benchmark sequence or static camera, restarted every cell) and which executable PresentMon targets. Their values are written to `docs/R1_SETUP.md` and committed before the first cell. A change to any of them voids the sweep. Chrome and tray apps are closed. In SOLO the LLM process is absent. The LLM process is started and the model loaded before the warm-up of its cell, with the game already running, and decodes from the start of the warm-up (amended 2026-11-11, see "Amendments"); tok/s is counted inside the measured window only. The LLM-alone reference cell is run in its own invocation with the game closed.

Preset acceptance, applied to SOLO data only: SOLO holds the 60 fps cap with GPU busy time per frame between 6 and 10 ms (median over a 20 s SOLO capture) and a hitch share below 1%. No loaded-arm result is looked at before the preset is frozen and committed in `docs/R1_SETUP.md`, together with the number of smoke runs. If the accepted preset cannot be found, the sprint stops and reports; it does not reinterpret.

## Arms and design

Each cell is 60 s measured after a 20 s warm-up. Arms: SOLO; UNGATED; PRIO_IDLE (the LLM process set to the lowest GPU scheduling class with `D3DKMTSetProcessSchedulingPriorityClass`, the status checked and the class read back at the start and end of the cell); DUTY50 (the LLM sleeps for its own measured token time after each token, no hint; reference only, see the rule); IGPU (the LLM on the Radeon 780M through the Vulkan backend; the build is timeboxed to one hour and the arm is dropped, with the reason recorded, if it fails). A separate LLM-alone cell gives the reference tok/s.

Five reps. In each rep the order is SOLO, then the four arms in an order shuffled from the seed 89770043, then SOLO again. Between cells the rig rests until the GPU temperature is within 3 C of the temperature at the start of the rep, for at least 30 s and at most 180 s, and logs the rest time. The reference for an arm in a rep is the mean of that rep's two SOLO cells, and comparisons are paired by rep. The signed difference between the closing and the opening SOLO of each rep is reported as drift, separately from the absolute difference, which is the noise.

Primary metrics, from PresentMon: the p99 of frame time and the hitch share. Secondary: p50, 1% low fps (1000 divided by the mean of the slowest 1% of frame times), GPU busy per frame, tok/s from the driver's per-token log inside the measured window only, GPU power from two reads of the NVML energy counter, VRAM used and temperature at the start and end, median SM clock and throttle-reason bitmask from a 50 ms NVML sampler that runs in every cell. "Frame time" is the PresentMon column named in the schema committed in `tools/realgame/presentmon.py`, taken from a real header captured in the smoke cell and committed before the sweep; frames PresentMon marks as dropped stay in the data. A cell is flagged as paging if the game's shared GPU memory (the PDH "GPU Process Memory" Shared Usage counter) exceeds its SOLO level by more than 64 MB.

No cell is excluded. A cell that fails (a crash, a PresentMon gap, a failed priority call) causes its whole rep to be rerun with the same seed, and every attempt is reported. Flagged cells (paging, throttling) stay in the rule and are listed. A PRIO_IDLE cell whose read-back is not the idle class makes PRIO_IDLE void for the sweep: it counts as not within limits and cannot support BUILD THE GATE. UNGATED is valid only if the LLM produced tokens throughout the window (tok/s above 25% of the LLM-alone reference); otherwise the sweep is voided.

## What the rule can resolve

A cell has about 3,600 frames, so its p99 rests on about 36 frames, which come in clusters. Under a hard cap the SOLO p99 sits near 17 ms, so the 5% limit is about 0.85 ms, close to the limiter's own jitter, and 0.5 pp of hitch share is about 18 frames. With five reps no significance is claimed (a Wilcoxon test cannot go below p = 0.0625); the decision uses the mean of the five paired values, the median and the worst rep are reported beside it, and a percentile bootstrap over the five values is reported for information only (it has 126 distinct resamples and undercovers, so it gates nothing).

## Decision rule (thresholds fixed now)

Per rep, the p99 worsening of an arm is its p99 minus the mean p99 of that rep's two SOLO cells, divided by that mean; the hitch increase is its hitch share minus the mean hitch share of the two SOLO cells, in percentage points. An arm is within limits if (a) the mean paired p99 worsening is below 5%, (b) the mean paired hitch increase is below 0.5 pp, and (c) no single rep has a worsening of 10% or more or an increase of 1 pp or more. An arm is harmful if the mean paired p99 worsening is at least 15% and the mean hitch increase is at least 2 pp.

Noise precondition (added in review, for the owner to confirm): a claim that an arm is within limits is allowed only if the mean over reps of the absolute difference between the two SOLO cells is below 2.5% in p99 and below 0.25 pp in hitch share, and the SOLO hitch share is below 1% in every rep. A harmful finding does not need the precondition.

Branches are evaluated in this order and the first that holds is declared.

1. NO PROBLEM: UNGATED is within limits (and the precondition holds). It is reported as holding for this preset and this game only; no heavier-preset rerun follows.
2. SIMPLE FIX: PRIO_IDLE or IGPU is within limits and keeps a mean paired tok/s ratio to UNGATED of at least 0.70 (IGPU: a mean tok/s of at least 15.0 inside the window with the game running, instead of the ratio). If both qualify, both are reported and the one with the higher tok/s is named the fix.
3. FIX TOO SLOW: UNGATED is harmful, PRIO_IDLE or IGPU is within limits, and neither meets its throughput condition. This is a result in itself: a fix protects the game at a cost in throughput that the rule judged too high, and the numbers are reported without a next step beyond that.
4. BUILD THE GATE: UNGATED is harmful, PRIO_IDLE is valid, neither PRIO_IDLE nor IGPU is within limits, and the predictability test passes. If the IGPU arm was dropped, the rule is evaluated on PRIO_IDLE alone (amended 2026-11-11) and the results document states that the IGPU option was not tested.
5. OPEN: anything else, including UNGATED neither within limits nor harmful. The follow-up for OPEN is declared now: one repeat of SOLO, UNGATED and the arm in question with 10 reps, under this same rule, and nothing else.

DUTY50 is reference only: it shows what a naive throttle does and cannot be the fix of branch 2 (the brief names PRIO_IDLE and IGPU; this is for the owner to confirm). Whether WDDM applies the priority class to compute queues submitted through CUDA is the experiment itself; there is no positive control, and a null result means "no effect observed with a verified read-back", not that the mechanism cannot work.

## Predictability test (offline, from the captures)

For each SOLO frame, predict its GPU start time from the cadence of the previous N frames: the previous start plus the mean interval over the window. N = 8 is the test; N = 4 and N = 16 are sensitivity checks and do not decide. The GPU start time is not a PresentMon column; I derive it as the CPU start time plus the GPU latency of the version-2 metrics, so the error is partly the error of that proxy, and the result says so. Report the p50, p95 and p99 absolute error in ms, the same error for the baseline that predicts "previous start plus 16.67 ms", and the distribution of GPU idle time per frame (frame time minus GPU busy). Because a gate needs the end of the game's GPU work and not only its start, the same prediction is made for the end of work (start plus GPU busy). PASS if, for N = 8 on SOLO, the p95 error of both the start and the end is at most 1.5 ms and the median idle time per frame is at least 3 ms. The idle condition follows from the preset acceptance (6 to 10 ms busy in a 16.67 ms frame) and cannot fail; the cadence conditions mostly measure the limiter. A pass is therefore necessary and not sufficient evidence for a gate, which is why branch 4 also requires UNGATED to be harmful. The same prediction is run on the UNGATED captures and reported as supplementary (the cadence under LLM overlap), without deciding anything. Not tested: live access to the capture with low latency.

## Forecast

Reference numbers, from the v1 characterisation and not from this machine in this configuration: the LLM alone unlocked gave 101.1 tok/s at 92 W; in the v1 smoke test an overlapped token took 2.05 times as long and an overlapped frame 1.95 times as long; the v1 time-slice fit implies each process runs at about 1/2.5 to 1/2.8 of its solo speed when both have work (assumed to carry over to a game). The forecasts are conditional on the preset satisfying the acceptance rule (SOLO GPU busy per frame 6 to 10 ms, central estimate 8 ms). They are guesses with ranges; I have not measured this game.

| Quantity | Forecast (range) |
|---|---|
| LLM alone, tok/s | 100 (85 to 115) |
| SOLO bracket: mean absolute p99 difference between a rep's two SOLO cells | 2% (0.5 to 6%); hitch share difference 0.1 pp (0 to 0.5) |
| UNGATED: p99 worsening | +35% (+8 to +120%); at 8 ms busy, 1.95 times gives 15.6 ms, just inside the deadline, so only the tail crosses it |
| UNGATED: hitch increase | +4 pp (0.5 to 30) |
| UNGATED: tok/s | 45 (30 to 65) |
| UNGATED: GPU power | 95 W (75 to 115) |
| PRIO_IDLE: p99 worsening | +20% (+3 to +80%) |
| PRIO_IDLE: hitch increase | +2 pp (0.2 to 20) |
| PRIO_IDLE: tok/s as a share of UNGATED | 75% (40 to 100%) |
| DUTY50: p99 worsening | +20% (+5 to +90%) |
| DUTY50: hitch increase | +2 pp (0.3 to 25) |
| DUTY50: tok/s | 26 (16 to 38) |
| IGPU: tok/s | 14 (8 to 22); probability of at least 15: 40% |
| IGPU: p99 worsening | +3% (0 to +15%) |
| IGPU: hitch increase | +0.2 pp (0 to 2) |
| Predictability: p95 error at N = 8, start | 0.6 ms (0.2 to 2.5) |
| Predictability: median GPU idle per frame | 7 ms (6.7 to 10.7, by the preset acceptance) |

Probabilities of the branch: NO PROBLEM 10%, SIMPLE FIX 25%, FIX TOO SLOW 10%, BUILD THE GATE 25%, OPEN 30%, with a 15% chance that the IGPU build fails and the arm is dropped (the rule is then evaluated on PRIO_IDLE alone and the IGPU option is reported as not tested; amended 2026-11-11). The first forecast I wrote put the UNGATED effect at +70% and NO PROBLEM at 3%; a reviewer pointed out that the 1.95 times figure I cited puts an 8 ms frame at 15.6 ms, and I revised the forecast down to what that number implies. Reasoning in one place. WDDM time-slices the GPU between processes, so a token that overlaps a frame stretches it; a flat-out decode overlaps most frames, but with 8 ms of busy time in a 16.67 ms frame only the frames that meet the longer slices or a stall cross the deadline. I expect the scheduling priority class to help only partly, because I do not know that WDDM applies it to CUDA compute queues. DUTY50 halves the duty but is not aligned to the frames. The iGPU leaves the game's GPU alone, so its cost is shared memory bandwidth and CPU; its tok/s is bounded by the system memory bandwidth over the 2 GB of weights read per token (the memory type and speed are read from the machine before the sweep; at a peak near 90 GB/s and 35 to 50% efficiency the estimate is 12 to 18 tok/s, so 14 is a guess near the 15 tok/s line).

## What the rule licenses

One benchmark, one preset, one scene, one cap method, one laptop, one model. A result is a statement about that configuration. It decides whether to spend the next engineering effort, and it does not show that a real game with variable load and CPU contention behaves the same, or that a 5% worsening of p99 is visible to a player; those limits go into the results document.

## Out of scope

No predictor-driven gate, no cb_eval port, no clock lock, no edits to any v1 or v2 registered file, no threshold tuning after data.

## Amendments before the first cell (2026-11-11)

Made after the Step 4 code reviews (Opus line-by-line, ECC security reviewer), before any cell was run. Each is a rule that the first draft left open or got wrong; none changes a threshold.

1. LLM start. The first draft had the LLM idle until the window opened. A reviewer showed that this puts the LLM's own start-up (lazy CUDA module load, graph capture) and the laptop's power and thermal transition from game-only to combined load inside the measured window, which flatters the loaded arms. The LLM now decodes from the start of the 20 s warm-up; tok/s and the energy window are counted inside the 60 s window only (`[t_open, t_close)`), and a context reset inside the window fails the cell (n_ctx 16384).
2. LLM-alone reference. Run in its own invocation with the game closed; it is the denominator of the UNGATED validity check. The first rig draft ran it with the game open, which would have lowered the reference to about 45 tok/s and made the validity check pass when it should void.
3. Gaps in the capture. A cell fails, and its whole rep reruns, if PresentMon's first window frame starts more than 0.1 s after the window opens, its last frame ends more than 0.1 s before the window closes, any gap between consecutive frame starts exceeds 0.5 s, or the window holds fewer than 0.95 x 3,600 frames.
4. UNGATED validity also requires that no gap between consecutive token ends inside the window exceeds 1 s, not only a mean tok/s above 25% of the LLM-alone reference.
5. Rest rule. "Within 3 C" is one-sided (temperature at most 3 C above the rep's starting temperature), because a cooler GPU needs no rest; rest applies between every pair of consecutive cells in the sweep.
6. Throttle flags. The raw NVML throttle-reason mask is recorded. SwPowerCap (0x4) fires on almost every loaded laptop cell, so it is a separate boolean; the throttle flag is any of 0x8, 0x20, 0x40, 0x80. Flags gate nothing.
7. Noise and branch 4. The claim "within limits" needs the noise precondition. Branch 4 uses the plain clauses (a), (b) and (c) without the precondition, so a nominally-within-limits fix under a noisy SOLO gives OPEN, and a plainly harmful UNGATED with failing fixes does not need the precondition. The condition "SOLO hitch share below 1%" applies to each SOLO cell, not their mean.
8. Predictor. A window of N frames gives N-1 intervals: the prediction is the previous start plus (previous start minus the start N frames earlier) divided by N-1. The baseline predicts the previous start plus 16.67 ms.
9. Interrupted reps. An unfinished attempt found on resume counts as a failed attempt and the rep restarts, so that the two SOLO cells of a rep are never hours apart.
10. Executable integrity. The harness refuses to run PresentMon unless its sha256 equals the value in "Conditions" (an explicit override is recorded in the meta file); the hash of each llama driver executable is printed and recorded. The harness runs from an Administrator shell because PresentMon capture needs ETW rights and the account is not in Performance Log Users; it records whether it is elevated.
11. IGPU. The arm runs only with a Vulkan-enabled build of the same pinned llama.cpp commit and is accepted only if the driver reports the Radeon 780M as the device. The owner installs the LunarG Vulkan SDK; the build is timeboxed to one hour from the moment the SDK is present, and the arm is dropped if it fails. This item supersedes the first draft's rule that a dropped IGPU arm forces OPEN: a dropped IGPU arm no longer forces anything, the rule is evaluated on PRIO_IDLE alone, and the results document states that IGPU was not tested.
12. DUTY50. Its sleep uses a high-resolution timer so that the achieved duty is near 50%; the achieved duty is reported with the result, and the arm stays reference only.
13. Owner confirmations (2026-11-11). The owner confirmed the four additions of the review: the noise precondition, DUTY50 as reference only, the added end-of-work prediction, and the setup file.
14. Noise, per rep. The noise precondition is also applied to each rep as it finishes: a rep fails if the absolute difference of its two SOLO p99 values divided by their mean is 2.5% or more, or the difference of their hitch shares is 0.25 pp or more, or either SOLO hitch share is 1% or more. A failing rep is rerun (a new attempt with the same seed order and every attempt kept). If more than 2 of the 5 reps fail the check at any attempt, the sweep stops and is reported. The limits are never loosened, during or after the sweep.
15. Clock state. The sweep is run with the GPU clocks unlocked. Before it starts the owner runs `nvidia-smi -rgc`; the harness then confirms that the admin clock helper is not running (its named pipe `governor_clock` is absent and no process runs `actuators/clock_helper.py`) and that the SM clock is not locked, and refuses to start a cell otherwise. NVML has no field that reports a lock, so the lock test is a heuristic that is fixed here and recorded in the meta file: with the GPU idle, an SM clock above 1000 MHz in P0 for 3 s counts as locked (an unlocked laptop GPU idles far lower), and a loaded cell whose SM clock is exactly constant for the whole window counts as locked and fails.
16. Elevation. The sweep runs from an elevated PowerShell because PresentMon capture needs ETW rights, so the LLM process runs elevated too; this is the same for every arm and is recorded in the meta file. It is not the normal-user condition for the LLM process and is a limitation of the results.
17. Display path. The laptop is in Standard (hybrid) GPU mode, so frames rendered by the RTX 4070 are presented through the Radeon 780M. This is recorded with the PresentMode column. If the IGPU arm runs, it loads the GPU that displays the game; its result holds for hybrid mode only.
18. Clock check (owner, 2026-11-11; supersedes the idle-reading lock test of amendment 15). On this laptop the idle SM clock moves between 720 and 1980 MHz across P0, P3 and P4 with no helper running, so an idle reading is not a lock test. The clock check loads the GPU for about 5 s with a CUDA kernel and records the maximum SM clock; PASS is a maximum above 1980 MHz under load and no clock-helper pipe. Idle samples, the power limit and the clocks-event reasons are recorded as information only. The `clock_check.json` gate of the sweep (passed, under 6 hours old) and the in-cell failure for an exactly constant SM clock over the window stay.
19. Power cap (owner). The harness refuses to start a cell unless the enforced power limit, read from NVML (`nvidia-smi` reports `power.limit` as N/A on this driver), is within 1 W of 95 W; the limit is recorded at the start and the end of every cell. The reading taken at setup was 92.77 W (see `docs/R1_SETUP.md`), so the rule refuses until that is resolved; it is not loosened.
20. Power measurement (owner). Power comes only from the NVML energy counter, two reads per window. Sampled NVML power is guarded (a sample above 1.5 times the maximum power limit, 210 W, is rejected, because this driver reports glitch values of about 590 W) and is recorded for information only; it is never used in any metric. The number of rejected samples is reported per cell as `power_rejected`.
21. Records (owner). Per cell: the idle VRAM (NVML used memory at the start of the cell, before the LLM loads) and the power limit. At sweep start: the full `nvidia-smi` process list and the display fields (Disp.A, display_active).
22. Elevation of the reference. The assistant's shell is not elevated, and the sweep must be started from the owner's elevated shell. Every cell records whether its process was elevated. The results document states whether the LLM-alone reference and the sweep arms ran with the same elevation.
23. Power limit (owner, 2026-11-11; supersedes amendment 19). The start-of-cell rule "enforced power limit within 1 W of 95 W" is dropped, because the enforced limit is dynamic on this laptop: readings of 83.7 W idle, 74.7 W in the first second of a load, 95.0 W after about 4 s of load and 93.8 W idle a few minutes later, so the rule passed or failed with the GPU's recent activity. The gate is now on the clock check: the maximum enforced power limit seen during its 5 s load must be at least 94 W, otherwise the sweep is refused and the owner is told to check the Armoury Crate mode. For every cell the enforced limit at the start, at the end, and its minimum and maximum over the measured window are recorded and never cause a refusal. The enforced limit is a recorded covariate: no threshold on it will be added after any data.
24. Static power fields (owner). At sweep start the default, minimum and maximum power limit from `nvidia-smi -q -d POWER` are recorded (observed: 80.00 W, 5.00 W, 140.00 W; the current limit, 92.82 W at that reading, is the dynamic field and is excluded). Whether they change with the Armoury mode is not known; the harness re-reads them at every cell start and refuses the cell if any of the three differs from the sweep-start value by more than 0.5 W, which also catches a mode switch during the sweep.
25. Elevation (owner; amends amendment 22). Every cell, including the LLM-alone cell, runs from the owner's elevated PowerShell, so all cells have the same elevation. The elevation is still recorded per cell.
26. LLM context size (owner, 2026-11-11; supersedes the 16384 of amendment 1). The LLM driver uses a context of 12288 tokens in every arm instead of 16384. Measured VRAM of the LLM alone on this card (8188 MiB, 454 MiB used at idle): 4139 MiB at 16384, 3687 MiB at 12288, 3235 MiB at 8192. At 16384 only about 3.6 GB would remain for the game, which risks measuring paging instead of scheduling; 12288 frees 452 MiB and still holds about 11,000 tokens, enough for an 80 s cell up to roughly 130 tok/s. A context reset inside the measured window still fails the cell.
27. Rest cap (owner, 2026-11-11; amends amendment 5). The maximum rest between cells is 300 s instead of 180 s; the 3 C target and the 30 s minimum are unchanged. A rehearsal of one 80 s LLM cell took the GPU from 45 C to 81 C, with a software thermal slowdown flagged, and it was back to 48 C about 2.5 minutes later, so 180 s could not reliably cool a hot arm. The start temperature of every cell remains a recorded covariate with no threshold on it.
