# Review: W2 Experiment B results (data/w2_B_results.md, uncommitted; raw run 20261021T105205Z)
Reviewer: Claude (cloud session). Status key: [FIX] before committing/reporting · [NOTE]

## Overall
HB1 is a clean, precise confirmation: fma service time scales exactly with the SM clock
(2.000 / 1.500 / 1.203 vs predicted 2.000 / 1.500 / 1.202, CIs ~±0.001). The pre-registered rules were applied as written.
Four things need fixing in how the results are labelled and explained, and there is one important finding
the report doesn't state.

## Findings
1. [FIX] HB2 with a memory background is labelled "NOT SUPPORTED", but the test is uninformative: the
   1800 MHz reference already misses 100% of frames (miss_frac = 1.0 in every membg cell, every level), so no level
   can be worse (ceiling; p = 1.0 by construction). Keep the registered verdict, and add next to it
   "uninformative: ceiling, reference already at 100% misses". The cause is by design: a saturating background
   (duty 1) plus a foreground needing ~53% of the GPU is > 100% demand at any clock. This arm can't separate clock effects
   from oversubscription. Record it in the journal as a design lesson.
2. [FIX] The mem-frame HB1 control fails at 900 MHz (observed 1.011 vs W1-derived 1.123). Not caused by the memory
   clock (W1 mem rows logged 8001 MHz at 900/1200/unlocked). Most likely W1's streaming kernel and B's mem frame kernel
   differ in compute per byte (W1's mem kernel was clock-limited below ~1200 MHz; B's frame kernel isn't), so W1 ratios don't
   transfer between "memory-bound" kernels. Same lesson as C: the knee is a property of the specific kernel, not of a
   workload class. State this explicitly. It matters for the governor, because it means the knee must be measured per
   workload (or learned), not looked up.
3. [FIX] Under co-run, fg_gpu_p50_ms behaves inconsistently: fma frames at 1800 MHz show 12.13 ms with background vs
   12.10 ms without (no inflation), while fma at unlocked shows 22.2 vs 8.86 ms and mem frames 24.2 vs 8.94 ms (2.5–2.7x).
   Before interpreting "service time" in any co-run cell, establish what the cudaEvent interval measures while the
   context is time-sliced out (does it include switched-out time?) and why the unlocked and locked fma cases differ. Do this
   with one Nsight Systems trace of fma_60hz_membg at 1800 and at unlocked (descriptive, not a new hypothesis).
   Until that's resolved, label co-run fg_gpu values "interval incl. possible switched-out time".
4. [FIX] Overload latency stats are computed over COMPLETED frames only (fg_incomplete 0.09–0.84), so they suffer
   survivorship bias; e.g. unlocked membg looks "faster" than 1800 membg while completing fewer frames. The registered rule
   already says not to interpret them. Make the report show completed-fraction next to every latency percentile in
   overloaded cells.
5. [FIX] Provenance: data/raw/w2_B/20261021T104818Z is a non-smoke run that stopped after 0 cells (header only). Record
   why in the journal (false start? crash? interrupted?) and state that 20261021T105205Z is the analysed run.
6. [NOTE] The finding the report doesn't state (descriptive; put it in the journal, not as a tested claim):
   deadline-aware clock locking saves substantial power at zero misses when the foreground has slack.
   - fma_60hz, no background: unlocked 56.5 W / 8.86 ms; 1800 MHz 38.5 W / 12.1 ms; 1500 MHz 31.9 W / 14.6 ms (p99 15.0 ms
     vs 16.7 ms budget), all 0% misses. That is ~43% less GPU power at 1500 MHz, but with only ~1.7 ms p99 margin.
   - mem_60hz, no background: 900 MHz 24.9 W vs 40.7 W unlocked, latency unchanged (9.10 vs 8.99 ms p50).
   This is classic slack-reclamation DVFS from real-time systems (e.g. Pillai & Shin, SOSP 2001: verify before citing).
   For the governor it means: pick the lowest clock whose predicted service time fits the deadline with margin, per workload.
   Together with finding 1, the design implication is that the background must be paced (duty < 1) for the foreground to meet
   deadlines at all. That's what A's secondary duty sweep measures, so A/A2 is now the most decision-relevant run.
