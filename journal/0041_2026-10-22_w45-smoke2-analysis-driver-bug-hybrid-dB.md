**What the data say (data/w45_smoke/smoke2_report.md, made by analysis/smoke2_report.py from overrun.json and overrun_raw_*.json; throughput from the driver's DONE line).**
- Token durations are bimodal when the fg runs: clean tokens 10.1 ms (the background alone: 10.03 ms, p99 10.9, 100.2 tok/s) and stretched tokens 20.7 ms (2.05x). Unaligned duty 1 with the fg: every token 20.45 ms, fg p50 13.12 ms (alone 6.7-6.9 ms): a frame and a token that overlap each slow each other by about 2x.
- In the aligned runs 27-30% of tokens are stretched (99% at duty 0.5) and ALL stretched tokens start at 15.67 ms after an arrival, i.e. exactly 1.0 ms before the next one = the fg's pace-block "busy" publish (FrameLoop lead_ms = 1.0). Clean tokens start 5.2-7.2 ms after the arrival (median 6.0), the neighbourhood of the frame-completion publish (fg median latency 6.78 ms, so the start phases sit slightly BEFORE the median completion; not resolved: per-frame completion times were not saved).
- The guard has no effect: guard 0 / 0.5 / 1 / 2 ms give the same long-token share (30 / 28 / 27 / 27%), start phases and 59.7-60.0 tok/s. The driver's own fit test (now + EWMA estimate + guard <= next arrival, estimate reconstructed from the logged durations) would have admitted 0.0-0.3% of the logged starts. So the tokens were not admitted by the test.
- The fg met the deadline in every run (miss 0.000, p99 13.5-13.7 ms), including the fully overlapped unaligned case (13.5 ms): at the nominal cost 7 ms, overlap is survivable. The overrun is harmless to the SLO at this cost and would matter at the 1.3x phases (9.1 ms frames, expected overlapped latency above the 16.67 ms deadline; an expectation, not a measurement).
- The smoke's own bg_tok_s for the background-alone run (57.2) is wrong: the driver stopped at the context limit after 15.3 s (1534 tokens, ctx_end 2046) and the script divided by the 23 s window; the true rate is 100.2 tok/s. Its whole-run mean power (60.4 W) is diluted the same way and is not used.

**Cause (mechanism reproduced without the GPU).** shm::Block::read gives up after 200 retries (microseconds) while the Python writer is mid-write; the driver treated a failed read as "pace block never written / fg idle" (busy false, next arrival +inf), so the fit test passed. Every fg publish (two per frame) opens such a window. tests/test_pace_view_cpp.py runs the real C++ reader against a Python writer emulating the frame loop: in 5 s the legacy policy saw 25368 phantom-idle polls (all of them failed reads), the fixed policy 0 (probe tests/cpp/probe_pace_view.cpp). That this is THE cause of the logged starts is supported by (i) the start phases coinciding with the publish moments, (ii) the guard independence, (iii) the 0-0.3% admission; it is not proven for each token (the driver did not log why it started a token).
**Fix.** workloads/background/pace_view.h (shm::PaceView): a failed read keeps the last good value; only a never-written block or a value older than 100 ms means "fg idle". llama_governed_bench.cpp uses it (source test: no bare pace.read). The exe was rebuilt (new hash; must be warmed once). The control block is not affected: a failed ctrl read leaves the previous values in place (the array is only overwritten on success).
**Consequence for the plant and the earlier smoke.** The smoke-1 plant comparison (journal 0038) and every number from the old driver describe a driver that ignored its own fit test; "aligned guard 0 is unsafe on hardware" should read "the unfixed driver did not honour any guard". The plant's overlap timing is still off (share divisor 2.5; the measurement says a token overlapped by one frame takes 2.05x and the frame 1.95x), but the sim is frozen.
**What the fix will probably expose (expectation, not a result).** At cost 7 ms the slack after a frame is about 9.9 ms and a clean token takes 10.1 ms: a correct fit test admits almost no tokens, so aligned slack-filling gives about 0 tok/s at that cost and the controller must either use a lighter frame cost, accept overlap (duty-cycle pacing; the fg tolerated it at 7 ms), or fit at another clock. This is also why HW0 (feasibility gate) must pick c0 on the tuning blocks: at 7 ms arm a does not miss (p99 13.5 ms), so the registered gate "a misses > 5% in S1" would fail at c0 = 7 ms and c0 has to be raised. Smoke 3 (docs/W45_SMOKE3_SETUP.md, 6 runs, about 5 min) checks the fixed gate at frame costs 4 / 7 / 9 ms.

**Learned-guard recommendation.**
1. Keep the design (guard grows by the observed token-end overrun past the next arrival, decays slowly): after the fix an aligned start with a finite next arrival is always rule-admitted, so an observed overrun is genuinely an estimation error and the signal means what the design assumes. Free-run starts happen only when the fg is idle (no next arrival, no overrun defined).
2. The signal must be confirmed by smoke 3 before W5a: at cost 4 ms (slack about 12.7 ms) tokens should fit with almost no long tokens; at 7 ms almost none start; at 9 ms none start.
3. Risk to handle after smoke 3, not before: the driver's token estimate is an EWMA of ALL token durations; one stretched token (20 ms) lifts it to about 11 ms and it needs dozens of tokens to recover, during which the fit test blocks tokens that would fit. Candidate fix: estimate from clean tokens only (those that ended before the next arrival). Not implemented: smoke 3 shows whether it matters.
4. The guard cannot create slack: when token time >= slack (the 7 ms case) the decision belongs to the model (other clock / duty-cycle pacing), not to the guard; the cap guard_fb <= 6 ms stays.

**Hybrid d'B written test-first (controllers/hybrid.py; tests/test_hybrid.py, 6 tests: RED = module missing, GREEN 6 passed).** Active ticks are exactly the learned ModelController (v2+v3, same actions on 30 synthetic ticks incl. overruns); after IDLE_TICKS (5) empty ticks the action equals the eB idle action (knee clock, aligned, duty 1, guard 0; compared with IdleDropController); idle observations (power 30 W, overrun 3 ms) leave pscale/pbias/pdelta/guard_fb/c_hat/tok_sd untouched; the first tick after idle returns a model action and skips the power calibration against the stale pre-idle plan (a 90 W observation leaves pscale and pbias unchanged); the learned guard still grows inside the hybrid. It is NOT run in the simulator and not registered in sim/run.py (frozen); it will be exercised on hardware in W5 only.
