- Decision log of choices the addendum left open: (a) fg records every request from the measured window (432,000 blocks for the 0.1 ms stream); bg records slices from the window start until an 800,000-block buffer is full (about 3,700 slices of 216 blocks: only ~1.9 s of timeline at m = 0.5 ms, ~7 s at m = 2; later slices run the plain kernel; dropped counts are in results.csv); (b) the "median loop-iteration gap" in the G_thr rule is implemented as the median over blocks of block duration / number of reads (storing every gap is infeasible); (c) the gap-read interval is 64 loop iterations.

## Incidents
1. First pre-check run crashed in block 1 (cell b01_00_g_R2: child rc 1). Cause: my kernel took the block start from thread 0 only, but another warp's gap could begin earlier, so gbeg - t0 wrapped to a huge unsigned value and `pack_rec` refused it (the guard worked). Fix: block start = earliest warp start, end = latest warp end; test added (gap lies inside the block span). Not reproducible deterministically; the fix is by construction.
2. Third run: ovh child failed, AttributeError w2_set_gap_stride: I had not rebuilt the DLL after changing the kernel source. Rebuilt; suite 147 passed.
3. Instrumentation cost found by the pre-check: the first recording kernel made bg slices 17% (harness cells: 2.42 vs 2.06 ms) and, in a controlled A/B, 1.5-1.7x longer at every read interval (64-512). The reads were not the cost: the branch inside the FMA loop was. Restructured into branch-free chunks with the read between chunks: ratio 0.999-1.004 at interval 64 (0.95-0.97 at 128-512, i.e. the chunked loop is faster than the original plain loop, which is why interval 64 was kept: typical read gap 2.0 us, G_thr about 41 us, far below the ~243 us switch gap; at 512 the typical gap would be 15 us and G_thr 300 us, which would miss it).
4. Thermal waits: the 14-cell smoke took 14.6 min because of start_temp_not_reached waits (up to 60 s per cell); the 55-minute estimate for the full run is not reliable, expect roughly 1.5-2.5 h (an estimate from this one smoke, not a measurement).

## Pre-check results (smoke grade: unlocked clocks, 3 blocks, non-admin; NOT the registered acceptance)
- (i) %globaltimer resolution: smallest nonzero step 1024 ns; 99.2% of consecutive reads in a tight loop are identical.
- (ii-a) one process, two streams: 216 + 216 blocks, 0 outside the host launch..done window (tolerance 119 us).
- (ii-b) two processes: the fg and bg children read the GPU timer against QPC at the same instant (<= 23 ms apart): offset differences -37 to +11 us against summed round trips 93-195 us, so one shared timebase within the measurement error; 0 of 431,568-432,000 fg blocks per cell outside their request's host launch..complete window. GPU timer drifts ~0.9 ms relative to QPC over a ~15 s cell (~60 ppm), handled by using per-cell mean offsets with a drift allowance.
- (iii) overhead: controlled A/B (iii-a) 0.999-1.004 at interval 64; harness R_2 on/off p50 differs by 1.0%, bg slice 2.004 vs 1.994 ms. The fg-alone and observed-wait criteria cannot be evaluated unlocked (the fg-alone cells idle at ~210 MHz: 17.6% and 0.044 ms differences are clock state), so they are NOT evaluated here.
- 14-cell smoke: all cells ran, 0 fg records dropped, bg buffer fills as designed (dropped slices recorded).
