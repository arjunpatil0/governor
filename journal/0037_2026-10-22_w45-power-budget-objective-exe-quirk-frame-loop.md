**Fresh exe "runs its body twice" - cause found (strong evidence, not proven).** data/exe_first_run_probe.md (analysis/exe_first_run_probe.py, tests/cpp/probe_start.cpp, test_shm.cpp):
- It is NOT a harness retry: it reproduced with Python subprocess.run and Popen+poll; every launch produced exactly ONE real process start (one pid line).
- A never-seen executable (new SHA-256) that writes to a NAMED shared-memory ring shows the ring side effect of TWO body executions on its first launch (ring pushes = 10, pid lines = 1), while a byte-identical copy or a rerun shows one (5 pushes). A never-seen exe that only appends to a file shows one start. First-run delays were 0.8-2.4 s in these tests (14 s once earlier).
- The active antivirus is Avast (AvastSvc running); Microsoft Defender is stopped and real-time protection is off (Get-MpComputerStatus, read-only). The most consistent explanation is Avast's pre-execution analysis of unknown binaries (emulation/sandbox) in which the program's named-object calls reach the real objects while its file I/O does not. I did not change AV settings and cannot see Avast's logs, so this is an inference.
- Consequence: any first run of a new binary can repeat side effects on named objects. Rule: warm every new exe once against throwaway names (workloads/common/exe_warm.py keeps a per-machine SHA-256 registry; the W5 run protocol requires it). The earlier W2 experiments loaded their kernels as a DLL in-process and wrote files, so I expect them to be unaffected (no named-object side effects), but I have NOT checked this against the harness code or run logs; the llama_decode_bench.exe runs (L) are the ones to check first, since that exe is a separately built binary.
